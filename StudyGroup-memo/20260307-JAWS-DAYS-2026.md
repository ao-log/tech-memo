#### 11:00 [A2]AWS IAM は誰の責任か？ ~ Cloud Infrastructure チーム が全部守る設計はなぜ失敗するのか

* 運用上の課題として IAM の払い出しがある。インフラチームがボトルネックになる
* 事故が起きないようにする責任はインフラチーム
* インフラチーム側で担当するもの
  * SCP (ただし、最低限)
  * 標準ポリシーの提供
  * ABAC
    * インフラチーム側では特定タグ付きリソースのみ操作可能なエンティティを提供
    * アプリチーム側ではリソースにタグを付与しておく
      * Create 系の操作はタグ付与必須にする


#### 11:30 [B3]200アカウント規模を見据えた開発・検証・本番の環境分離を成立させる、AWS Transit Gatewayによるネットワーク設計と実践

* Control Tower アカウント配下の環境
* ネットワーク専用のアカウントを設けている。Transit Gateway で接続
  * 本番環境用、検証、開発環境用で別々に Transit Gateway などのネットワーキングリソースを作成し、環境間の分離
    * オンプレ経由などで環境間の通信ができてしまうリスクがあったので、ルートテーブルで宛先 CIDR を Blackhole に設定。CIDR は環境毎に別々になるように設計
  * コスト最適化のため、集約アカウント上に Route 53 Resolver, VPC Endpoint を設置
    * Private Hosted Zone を使用
  * 各アカウントへのリソース作成
    * Account Factory For Terraform でアカウント作成および各リソース設定を自動でできるようにした


#### 12:00 [D4]Amazon Q Developerをクライアントワークで、チームで導入した話

* 導入のハードルが低いのが利点。エンドユーザーサイドとしても稟議を通しやすく選定しやすい

  * テスト用データの作成

  * ただし、システムの全体像であったり複雑な内容は効果が出にくい。逆にいうと、疎結合、個々を小さくすることが効果向上のポイント

#### 12:20 [D5]そのツール、全部使えて大丈夫？　～ランチ15分で学ぶ、Okta × Bedrock AgentCoreの認可制御レシピ～ 

* エージェントの権限が強いと、エージェントが勝手に破壊的な操作をした時の影響が厳しい
* Slack で特定のコマンドを実行すると API Gateway 経由で Lambda Invoke から Agent Core を呼ぶ流れ。ここで認可を動的に判定して、判定に通ったら使用したいツールを実行する
  * Agent Core にて認証情報に対応する属性情報(役職、部署など)などは Okta から提供される。認可のチェックをコード内に統合できる
  * Verified Permissions は認可エンジン
    * Cedar ポリシー言語で記述できる。CW Logs に Allow, Deny を記録し、監査ログとしても活用できる
    * 緊急時に全部 Deny のようなポリシーも適用できる


#### 12:40 [D6]作りっぱなしで終わらせない！価値を出し続ける AI エージェントのための「信頼性」設計

* AI Agent 設計
  * マルチエージェントを前提とする。役割を限定して特化
  * MCP などで外部接続。CLI で効率的に接続することも必要に応じて使い分け
  * AI Agent の動作もテレメトリーから確認、説明
* Strands Agents [Strands Agents – オープンソース AI エージェント SDK の紹介](https://aws.amazon.com/jp/blogs/news/introducing-strands-agents-an-open-source-ai-agents-sdk/)
* Bedrock AgentCore 上で動かす
* AI Agent の自律動作
  * Agent 側で実行計画を立てて必要に応じて各種ツールを呼び出していき、結果を返す (Agentic loop という)
    * 中でどういうツールが呼び出されているかはブラックボックスになりがちだが、オブザーバビリティを確保していくのが大事
* AI エージェントの評価
  * 品質、レスポンスなどのパフォーマンス、エラー率、コスト、ガードレールが機能しているかなど
  * LLM as a judge の考え方がる。LLM が評価者として、評価を定量化していく
* Datadog x AI
  * LLM Observability
    * AgentCore Runtime 側で環境変数とトレース用のコードで LLM 実行内容のトレースを Datadog 側にトレース送信できる。中でどのようなツール呼び出しがあり、どの程度の時間を要したかなども可視化できる
    * ハルシネーションや言語不一致、ガードレール機能しているか、プロンプトインジェクション、カスタムとして感情分析なども LLM で評価してくれる
  * 信頼性の設計
    * SLO は過剰な厳密性を避ける


#### 13:20 [B7]クラウド × シリコンの Mashup - AWS チップ開発で広がる AI 基盤の選択肢

* Nitro System
  * ネットワーク、ストレージ仮想化などは専用ハードウェア(Nitro Card)にオフロード
  * 多様なインスタンスタイプ提供、最大限の性能提供、セキュリティ向上につながる
  * EFA: SRD によるスループット、レイテンシーの改善。複数ネットワーク経路を活用するマルチパスルーティング
* Graviton
  * ARM なので、ソフトウェアエコシステムも重要
  * マネージドサービスも対応
  * 消費電力削減効果が高い
* Tranium / Inferentia
* AI 時代のチップ選択
  * いかに効率よく行列計算（積和演算）を実行できるか
* Tranium
  * シストリックアレイでは、隣のコアとのみ情報共有する。そうすることで効率が良くなる
  * ANTHROPIC の claude model は AWS では Tranium 上で稼働している。OpenAI も大量に使う契約をしている
  * NeuronLink でチップ間を接続
  * Tranium3
    * 2.52 PFLOPS
    * 大容量メモリ
    * ラック内に 144 個のチップ
    * サーバ筐体内には 4 個のチップ、Nitro Card, Graviton も
    * Neuron Switch で接続
* Neuron
  * Tranium, Inferentia 向け SDK
  * Native PyTorch。GPU と同様に使用できるように
  * Neuron Kernel Interface (NKI)
    * コンパイラやライブラリなど
  * Neuron Explorer
    * パフォーマンス最適化とデバッグを支援


#### 14:20 [A9]AWS×クラウドネイティブソフトウェア設計――依存を「選ぶ」イベントドリブンアーキテクチャ

* 特定の処理が遅い場合、その部分のみスケーリングしたい
* ただ、バラすとなると、二層コミットメントなどの面倒な話も出てくる
* 依存性をどう扱うか
  * 密結合になっている場合は、API やプロトコルでやり取りするようにする
  * 間にインタフェースを挟む
  * 非同期で扱う
* イベントドリブン
  * DynamoDB Streams (データの変更などが契機でトリガー) → Kinesis → Lambda のような流れ
  * SQS → SNS のような流れ
  * MSK → ECS/Fargate
* at least once などの考慮が必要
  * 同じ ID が来たら弾くようにして Exactly Once にすることで、冪等性を確保

#### 16:20 [B13]変化に耐える設計、その定義が変わる ～レジリエンスから再生成へ。 AI時代のシステム設計論～

* キーノートで出てきたマインドセットは実はアナログ要素があり、人間側のキャパシティやチームのコミュニケーション能力が大事
* システム設計とは何のために行うか
  * 人間は要件の整理や制約などを課して、AI で自動化していく方向性
  * リポジトリが分散したり、コードベースが 100 万行規模の場合は？
    * Blackbox 化した部分を、既存部分を壊さずに対応していく必要がある
  * スタートアップの場合は
    * 速度がここ数年でガラッと変わっている
    * 従来コードを書きながら設計を固めていくようなものもあった。シニアなエンジニアは使いこなせそうだが、ジュニアなエンジニアには厳しい
* 実装負荷は下がっているかどうか。下がっている場合は解き放たれるものは？
  * 負荷が低下している部分とそうでない部分がある
  * ミッションクリティカルなシステムだと、AI を活かせる部分が少なかったり、活かそうという意思決定に結びつかないこともありうる
  * ボトルネックの箇所がどこかに注目する必要がある。また、レビューの意義もチーム内のメンタルモデルになったりしている部分もあり、単純に AI で代替して生産性を上げる選択肢を取るのはどうなのかとは考える
  * コードにより起こったことを説明する責任は常に人間にある
* いつでも使えるサービス(高可用性)の再定義をしてみたい
  * 耐障害性の観点では、運用エンジニアが学習のサイクルを回すことも重要であった。AI 時代ではそのループが高速化するとも言われている。AI の能力や進歩が早く、人間側が適応障害的な状況になる可能性もある
  * AI だから不安定、というわけにはいかない。そのため、AI の採用をすればいいというものでもないのだが、スピード等とのトレードオフなので、取捨選択が必要。現在は運用ツールでも AI Agent が使用されている部分もあるが、最終的な部分は人間が判断する
* 現在はジュニアなエンジニアだと使いこなせない感じもするがどうだろうか
  * もう少し進歩してくると、生成されたコードを読まなくてもいい未来になっていくかもしれない。現時点で、低レベルな部分を意識しなくてもいいように
  * 逆に相対的に自身でのプログレッシブな学習が重要
* 10 年後も動いていることの価値
  * 自分たちが説明できる状態のシステムを目指す必要がある
  * scrap & build が加速している
  * ダメだと思えば作り直すという判断もあるがどう考えるか。技術的負債を返済するという考え方も変わっていく可能性もある
  * 機械に任せる部分は増えるが、AI は手足の部分にするべきである
* [takt](https://zenn.dev/nrs/articles/c6842288a526d7) は革命的なツール。決定論的動作に落とし込むためのツール。何回も loop を回して、決定論的動作になるようにする
